# 反调试（客户端 JS）

> **定位**：单文件客户端反调试脚本 —— 检测开发者工具是否被打开、关键原生函数是否被 hook，命中后进入无限 `debugger`，用来抬高页面被断点调试、抓包、改包、分析源码的成本。
> **执行端**：客户端浏览器　**语言**：JavaScript　**依赖**：无（单文件、零依赖，引入即生效）

## 0. 一句话说明

把 `反调试.js` 放到页面 `<head>` 最靠前的位置即可：脚本**加载时先同步自检一次**（早于页面渲染），之后每 1000ms 复检一次；一旦命中「正在被调试 / 控制台已打开 / 关键原生函数被改写」，就进入无限 `debugger`，页面卡在断点循环里，直到你在 Console 执行 `window.stopAntiDebug()`。

## 2. 怎么引入

### 2.1 外链引入（推荐）

```html
<head>
  <!-- 放在 <head> 里，且要早于页面上其它脚本 -->
  <script src="/js/反调试.js"></script>
</head>
```

**不要加 `defer` / `async`** —— 两者都会把执行推迟到 HTML 解析完成之后，等于放弃「加载即自检」这条防线，重新打开「先开控制台再刷新」的窗口。

### 2.2 内联引入

不想多一次请求、或不想让人一眼看出是哪个文件时，把全文粘进页面即可（它本身是 IIFE，不需要再包一层）：

```html
<head>
  <script>
  /* 把 反调试.js 全文粘贴到这里 */
  </script>
</head>
```

### 2.3 位置与顺序（要点）

| 要点 | 原因 |
| --- | --- |
| 放在 `<head>` 最靠前 | 自检发生在脚本执行的那一刻，越早越能拦住「控制台先开着再刷新」 |
| 不要放进 `DOMContentLoaded`、动态 `import()`、打包器的懒加载 chunk | 那些都是页面渲染之后才执行，自检的意义就没了 |
| 同一页只引一次 | 重复引入会装两个定时器，每秒检测两次、控制台输出也翻倍 |

### 2.4 三步验证是否生效

1. 打开页面（**先不按 F12**）→ 页面一切正常；
2. 按 F12 打开 DevTools → 最多 1 秒内被 `debugger` 打断（Sources 面板停在断点处）；
3. 在 Console（暂停状态下也能用）执行 `window.stopAntiDebug()`，再按 F8 继续 → 恢复正常。

## 3. 对外接口

| 接口 | 说明 |
| --- | --- |
| `window.antiDebugCheck()` | 同步复检一次。`true` = 通过（没被调试 / 控制台没开 / 关键原生函数没被改写）；`false` = 命中，并且已经启动无限 `debugger` |
| `window.stopAntiDebug()` | 关闭反调试：置内部标记 + 清掉定时器，之后 `antiDebugCheck()` 恒为 `true`（一次性、不可恢复） |

两个函数挂在 `window` 上，页面里、控制台里都能直接调用。**这两个名字是唯一入口**，脚本不写全局其它变量。

***

## 4. 检测原理（三种手段）

命中任意一条即进入无限 `debugger`（用 `setTimeout` 递归实现，而不是 `while(true){debugger}` —— 万一误判，页面只是变卡，还能执行开关跳出来）。

| 手段 | 触发条件 | 原理 | 什么情况下会失效 |
| --- | --- | --- | --- |
| `debugger` 计时 | 单次 `debugger` 执行耗时 > `PAUSE_THRESHOLD`（默认 200ms） | 动态生成一条 `debugger` 语句并执行；真的被调试器暂停时，耗时必然异常变长。`performance.now()` 与 `Date.now()` **双时钟取大者**，单一时钟被 hook 静止也能测出来。语句每次带随机后缀重新生成，「不在此处停止」拉黑的是上一个脚本，下次照样命中 | 站点 CSP 禁 `eval` 类构造（`Function(...)` 抛错，被 `try/catch` 吞掉，本手段自然失效，其余手段兜底）；DevTools 里关掉了 "Pause on debugger statement"；主线程被超长任务或 GC 阻塞造成的计时偏差会**误判** |
| 控制台探针 | 控制台面板**真的在渲染**被 `console.log` 的对象 | 给一个临时 `div` 挂 `id` 的 getter 再 `console.log`：只有控制台读取该属性时才会触发 getter。不依赖「暂停」，所以「停用断点」这类开关绕不过它 | 控制台没打开（对象不会被展开渲染）；不走控制台渲染的远程调试通道 |
| 原生函数完整性 | 任一被校验函数不再是 `native code` | 校验 `Function.prototype.toString`、`setInterval`、`setTimeout`、`performance.now`、`console.log`。改写它们是绕过前两种手段的常见前置动作 | 明知故犯地伪造 `toString` 返回值即可绕过 —— 本手段只提高成本，不能根除 |

判定顺序是 `tampered() → paused() → consoleOpened()`，其中原生函数校验放最前：它不产生控制台输出、没有副作用，而且一旦被 hook，后面两种手段的结论本就不该信。

**检查节奏**

1. **加载时同步自检一次** —— 早于页面渲染、早于任何业务放行。所以「先开控制台、再刷新页面」会在渲染出任何内容之前就被按住，不会出现「主页面先渲染出来、1 秒后才被抓到」；
2. 之后每 `CHECK_INTERVAL`（默认 1000ms）复检一次，兜住「页面打开之后才打开控制台」的情况。

## 5. 配置项

改 `反调试.js` 顶部的常量即可：

| 常量 | 默认 | 作用 | 调整影响 |
| --- | --- | --- | --- |
| `CHECK_INTERVAL` | `1000` | 复检间隔（毫秒） | 调小更紧，但每秒的检测开销与控制台输出更密 |
| `PAUSE_THRESHOLD` | `200` | 单次 `debugger` 耗时超过该值即认定「正在被调试」（毫秒） | 调小更敏感，也更容易被长任务/GC 误判 |
| `BREAK` | `['debu', 'gger'].join('')` | 拼出 `debugger` 关键字，避免源码里出现完整字面量被静态扫描直接命中 | 一般不用动 |

**开销提示**：脚本每轮会做 1 次 `console.log`、1 次 `Function` 构造、1 次临时 DOM 元素创建。控制台打开时每秒会多出一条 `<div>` 日志 —— 这是控制台探针的正常输出，不是报错。

## 6. 和业务代码配合：放行前同步复检

反调试是 1s 轮询的，而业务放行往往在 `DOMContentLoaded`（几十毫秒）就发生。**只靠轮询挡不住「先开控制台再刷新」**，所以放行前要再同步确认一次：

```html
<script src="/js/反调试.js"></script>
<script>
document.addEventListener('DOMContentLoaded', function () {
  // 第零层：反调试没引入、或被拦截、或复检不通过 → 一律不放行
  if (typeof window.antiDebugCheck !== 'function' || !window.antiDebugCheck()) {
    return;
  }
  // 通过后再走你自己的业务判断
});
</script>
```

两点提醒：

1. 把复检放在最前，等于把「已被调试」的窗口压到最小；代价是**业务从此依赖这个脚本** —— 它被拦掉或加载失败时页面就永远不放行，这是有意的安全默认；
2. 反过来，如果只想让反调试作为「辅助噪音」而**不参与放行**，那就不要调用 `antiDebugCheck()`，让它自己后台轮询即可。

## 7. 常见问题

| 现象 | 原因 / 处理 |
| --- | --- |
| 控制台每秒多一条 `<div>` 记录 | 反调试的控制台探针输出，属正常现象；执行 `window.stopAntiDebug()` 后不再增长 |
| 一打开 DevTools 页面就卡在断点 | 预期行为。Console 里执行 `window.stopAntiDebug()`，按 F8 继续即可；这个操作**被暂停时也能做** |
| 页面进入死循环，Console 也像卡住了 | 死循环是 `setTimeout` 递归，每次暂停后都会让出事件循环，Console 仍可执行开关；先执行 `stopAntiDebug()` 再按 F8 |
| 页面永远空白且没被卡住 | 说明业务侧把复检当成了放行前置（见第 6 节），而反调试被拦下或误判了。在 Console 看 `typeof window.antiDebugCheck` 与 `window.antiDebugCheck()` 的结果即可定位 |
| 自己调试时一直被拦 | 页面加载后先执行 `window.stopAntiDebug()`，本次会话就永久放行 |
| 某些浏览器/环境下不生效 | 见第 4 节「什么情况下会失效」，最常见是 CSP 禁 `eval` 与 DevTools 关了断点开关 |
| 加了广告拦截/安全插件后频繁误判 | 部分扩展会包装 `console.log` 或计时函数，触发原生函数完整性校验。给该站点禁用该扩展，或用 `stopAntiDebug()` 放行 |

## 8. 已知局限与风险

1. **只能提高成本，不能阻止分析**：`view-source:`、curl/代理直接抓源码、禁用 JS、换没有调试器的浏览器，全都不受影响。
2. **原生函数校验可被伪造**：`toString` 的返回值本身就能改写（脚本注释里也写明了这一点），这条只是抬高门槛。
3. **存在误判可能**：主线程长任务/GC 造成的计时偏差、浏览器扩展对 `console` 与计时函数的包装，都会把正常用户判成攻击者 —— 所以死循环用 `setTimeout` 递归而不是 `while`，留出跳出的机会。
4. **误判代价是「页面不可用」**：如果把复检作为放行前置，被误判的正常用户（开着控制台的开发者、装了相关扩展的访客）会直接看到空白页。上生产前请评估这一点。
5. **与监控/上报类脚本可能互相干扰**：性能监控、错误上报、埋点 SDK 常常包装 `console` 与计时函数，混用时容易互相误判，建议先在目标环境实测。
6. **移动端基本不触发**：检测的是调试器/控制台/hook，与设备无关；手机上一般没有这些，等于不生效。
7. **没有「服务端」成分**：纯客户端，不产生任何网络请求，也不上报数据。
