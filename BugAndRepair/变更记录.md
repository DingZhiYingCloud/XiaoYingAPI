### 1. 新增：接口公告（服务 / 线路 / 端点三级公告栏，前台文档中心展示）

**背景**：运营需要在官网文档中心发布「该接口参数即将调整」「本线路正在灰度」这类临时通知。原先只能改文档声明源码，无法按接口粒度发布、也无法定时上下线。经确认的方案是：**服务 + 线路 + 端点三级挂载**；一条线路 / 端点**可挂多条、依次平铺**；公告正文**不做翻译**（后台填什么语言就显示什么语言）；控制项含级别配色、生效时间段、启停、排序。

### 2. 修复 + 优化：接口公告条的前端 UI 与交互（并修掉注释被渲染成正文的缺陷）

**缺陷（上一版引入）**：文档页公告卡片上方会多出一段中文说明文字。原因是 `API/templates/docs/_announcements.html` 顶部用了**跨行的 `{# … #}` 注释**——Django 的 `{# #}` 只支持单行，跨行写法不会被解析，会原样渲染成页面文本（`locale/多语言开发指南.md` 第 4 条「容易踩的坑」已写明，本次仍踩中）。已改为 `{% comment %}…{% endcomment %}`，并全量扫描 `API/templates/**/*.html` 确认无其它跨行 `{# #}`。

**UI / 交互重做**（原版是 `alert alert-{level}` 直接铺开，长文会把文档页撑得很长、也没有任何交互）：

### 3. 修复：页头下拉框（主题 / 语言 / 用户 / 移动端菜单）点击外部不收起

**现象**：点开页头「主题」或「语言」下拉后，点页面其它空白处不会收起，必须再点一次同一个按钮才能关掉。

**根因**：这些下拉是 `<details class="dropdown">`，靠浏览器原生行为开合 —— 原生 `details` 只响应「点自己的 `summary`」，对「点外部」没有任何处理（这是 HTML 规范行为，不是 daisyUI 或本项目的 bug，但交互上不合理）。

**修复**：在全局脚本 `API/static/js/site/ui.js` 里加一个 `document` 级 `click` 监听（注册在默认动作之前），只做「收起」、不干预展开：

| 点击位置 | 行为 |
| --- | --- |
| 下拉框之外的任何地方 | 关闭所有已展开的下拉 |
| 另一个下拉的 summary | 关闭其它下拉（保证同时只展开一个），由原生行为展开被点的那一个 |
| 下拉面板内部（选主题、点语言项、点搜索框） | 保持展开，不误关 |

同时把 `API/templates/template.html` 里 `ui.js` 的版本号从 `?v=20260909a` 提到 `?v=20260930a`（否则老页面会继续用浏览器缓存的旧脚本）。

**验证**（`.venv` + `manage.py runserver`，真实 Chrome，`/docs/`）

| 场景 | 实测 |
| --- | --- |
| 点「主题」展开 | `details.dropdown[open]` = 1 |
| 点标题区空白（非交互元素） | `[open]` = 0，已自动收起 |
| 点「语言」展开后点正文空白 | `[open]` = 0 |
| 先展开「主题」再点「语言」 | `[open]` = 1，且是「语言」（互斥生效） |
| 点下拉面板内的搜索框 / 面板内边距空白 | `[open]` 仍为 1（不误关） |
| 回归：切主题 | 点「明亮」→ `data-theme=light`，点「暗黑」→ `data-theme=dark`，切换正常 |
| 控制台 / 其它区域 | 无 error 报错；header 高度、侧边栏链接数、卡片数均无变化，下拉定位正常 |

**顺带发现（未改动，仅记录）**：主题下拉的搜索框按**中文标签**过滤（比较的是列表项文案），输入英文主题 id（如 `dark`）会把 35 项全部过滤掉、看起来「搜不到」。这是既有行为，与本次修复无关，需要的话可另行调整为「中文名或英文 id 任一命中」。

### 4. 重构：AI 服务改为「厂商 + 模型注册表」，DeepSeek 落地为首家厂商

**背景**：原 AI 服务把「DeepSeek 的地址与 Key」写死在 `.env`（`DEEPSEEK_API_KEY` / `DEEPSEEK_API_URL`），模型与能力也在代码里固定，接第二家厂商（Kimi / 豆包 / 千问）必须改代码。目标是**调用方只改 `model` 一个参数即可无缝切换厂商**，平台侧把「上游地址、密钥、模型能力」全部收口到后台配置。经与需求方两轮确认后的方案：建表 + 后台页；新增统一 `/chat` 并保留旧路径；前缀续写下线；视觉只收公网图片 URL；厂商表与模型表拆分；`api_key` 参数保留但只管调用方自己的 Key；后台要「测试连通性」；本轮先只落地 DeepSeek。

**过程中发现并修复的三个自身缺陷**

1. **`resolve_target()` 的 `or pool[0]` 静默兜底**（由回归脚本抓到）：「平台没有默认模型」时不报错、反而随便挑一个返回。已改为：不传 `model` 且未限定厂商时**明确返回 50002**，只有旧路径别名（已限定厂商）才回落该厂商的第一个模型。
2. **位置参数文案漏提取**：`EndpointSpec('models', '模型清单', …)` 的端点名是**位置参数**，而生成词条时用的是「只认关键字参数」的 AST 匹配，导致 `模型清单` / `AI 对话（统一入口）` / 模型 / 图片地址 等 8 条文案在 en / zh-Hant 下静默回退成中文。已改为**直接遍历声明对象**取文案（与 `localize()` 同口径）并补齐词条；同时清理了因 `docs/ai.py` 重写而失效的 7 条孤儿词条（前缀续写 / DeepSeek Beta 相关）。
3. **后台弹窗提交被拒「不支持的操作」**（由浏览器实测抓到，服务端直调用例抓不到）：两个表单片段把 `form_action` 同时当成「提交值」和「新建/编辑判断」，调用处传的是 `create` / `edit`，于是隐藏域渲染成 `action=create|edit`，而 `_handle_post` 只认 `provider_create` / `provider_edit` / `model_create` / `model_edit` 这类带前缀的动作名，因此新建 / 编辑弹窗全部落到「不支持的操作」兜底分支（行内按钮不受影响，因为它们的表单写的是正确动作名）。修复：表单片段拆成两个参数——`form_action` 才是提交给后端的动作名，`form_mode` 只用于模板内判断新建 / 编辑；同时把 `console_ai` 的动作表整理为 `_CREATE_ACTIONS` / `_PROVIDER_ACTIONS` / `_MODEL_ACTIONS` 并导出 `ACTIONS`，回归脚本据此对渲染结果做「页面上的 action 取值必须全部被后端接受」的闭环比对（第 53 条用例），防止再次脱节。

### 5. 新增：文档页在线调试支持「流式逐字打印」，SSE 增加独立的思考过程字段

**背景**：AI 接口传 `stream=true` 时，官网文档页的在线调试看不出任何流式效果——结果区总要等整段回答生成完才一次性出现，只能用「一次性显示 SSE 原文」来解释。

**根因（两层，缺一不可）**

1. 服务端代调把整条流抽干了：`API/website/docs_views.py` 对流式响应执行 `b''.join(response.streaming_content)`，读完全部再序列化成一次性 JSON 返回。这是当初为修「流式响应没有 `.content` 导致调试接口 500」而做的处理，代价是丢掉实时性。
2. 前端只认一次性 JSON：`API/static/js/site/docs.js` 用 `fetch(...).then(res => res.json())`，必须等响应体结束才有结果，再整段写进 `<pre>`。

**改动**

| 位置 | 改动 |
| --- | --- |
| `API/website/docs_views.py` | 新增 `_stream_through()`：**内层响应是 `text/event-stream` 时**改为返回 `StreamingHttpResponse` 逐块透传（并置 `X-Accel-Buffering: no` 防 nginx 缓冲），迭代 `streaming_content` 驱动视图生成器，因此上游吐一块就转发一块；结束时关闭内层响应。判断放在 `_is_textual` 之前（`text/event-stream` 也属于 `text/*`，否则会被当普通文本整条读完）。**其余响应（普通 JSON / 二进制流）分支一行未动** |
| `API/apis/ai/BuiltInModel/utils.py` | `stream_chat_completion()` 新增 **`reasoning` 帧**：推理模型的思考过程以 `data: {"reasoning": "…"}` 独立下发，与答案 `data: {"content": "…"}` 分开，只关心答案的调用方忽略该字段即可（原先只取 `delta.content`，思考内容被静默丢弃） |
| `API/static/js/site/docs.js` | 新增 `renderStream()`：用 `ReadableStream` 边收边解析 SSE 帧并**逐字追加**；思考过程渲染成灰色小字、答案正文渲染进 `<pre>`，二者分离；支持错误帧（流开始前出错，如上游 401）与 `[DONE]` 结束态；无 `ReadableStream` 的老浏览器退化为一次性读取。JSON 分支调用顺序随之调整，`fileFields`（multipart）分支不变 |
| `API/templates/docs/service.html` | `docs.js` 版本号 `?v=20260929f` → `?v=20260930b`（否则浏览器会继续用缓存里的旧脚本） |
| `API/website/docs/ai.py` | 流式说明改为「逐帧格式（content / reasoning）+ 在线调试会逐字打印 + 推理模型给出答案前会先流一段思考内容」 |
| `locale/en`、`locale/zh_Hant`（含 `.mo`） | django 域：流式说明换成新文案，并清掉一条因前面改措辞而失效的孤儿词条；djangojs 域：新增 3 条（流式接收中… / 流式接收完成 / 请求失败）。编译后 en 2107 条 + djangojs 163 条 |
| `README.md` | 第七章第 8 节补「流式返回」的两种帧说明与「在线调试可逐字打印」 |

**行为**：`stream=true` 时文档页结果区随上游产出逐字出现；推理模型会先出一段灰色小字（思考过程），之后才输出答案正文，因此开流式后前一两秒只有思考内容、没有答案属正常现象。非流式响应与其它所有接口的调试行为完全不变。

**验证**

| 项 | 结果 |
| --- | --- |
| 服务端代调（真实签名） | `POST /docs/_call/` 对 AI 流式调用返回 `text/event-stream` 且 `streaming=True`；实测 **338 个分片按时间推进到达**（首片 1594 ms → 末片 3208 ms），确认是逐块透传而非「读完再返回」 |

### 12. 优化：短剧网页直出支持按次选画质（play 的 q 参数），默认档由「高 720」改为「宽 1080」

**背景**：反馈出流画质偏低。逐层核对后确认**不是源站没有高清，而是转码参数压的**：

| 来源 | 分辨率 | 码率 |
| --- | --- | --- |
| 源站最高轨道 | 1080×1920 | 540 kbps |
| 本站在改动前的出流 | **408×720** | 1478 kbps |

主因是 `HONGGUO_STREAM_HEIGHT=720` 按**高度**缩放，而短剧是竖屏 1080×1920 —— 按高度缩到 720，宽度就只剩 **408px**；再叠上码率上限 1800k / CRF 26，又压一道。

**改动**

| 位置 | 改动 |
| --- | --- |
| `API/apis/dramas/hongguo/utils.py` | 新增画质白名单 `QUALITY_WIDTHS = (1080, 720, 540, 480, 360)`（值 = 输出**宽度**上限，竖屏即日常说的 1080p / 720p）与 `parse_quality()`；`make_stream_token()` 把画质写进令牌（出流端点只有 token 一个参数，画质跟着令牌走，URL 上改不动）；`get_play()` 增 `quality` 参数并在 `data.quality` 回报 |
| `SpiderServices/dramas/hongguo/transcode.py` | 全链路按画质参数化：产物路径 `{DIR}/{剧集}/{画质宽度}/{集}.mp4`（每档独立缓存）、任务键、锁、`ensure/is_ready/job_status/stream_path` 均带画质；缩放改为按**宽度** `scale=min(W,iw):-2`（源更小则不放大）；码率上限改为分级表 `_RATE_BY_WIDTH`（1080→3000k … 360→600k），硬件编码器目标码率取上限 75%，libx264 走 CRF（默认 26→20）+ 上限兜峰 |
| `API/apis/dramas/hongguo/request.py` | `play` 接受 `q`（非法值返回 20003）；`stream` 按令牌里的画质出流 |
| `XiaoYingAPI/settings.py`、`.env.example`、`README.md` | 下线 `HONGGUO_STREAM_HEIGHT` / `HONGGUO_STREAM_BITRATE`，新增 `HONGGUO_STREAM_QUALITY`（默认 1080）；`HONGGUO_STREAM_X264_CRF` 默认 26→20 |
| `API/website/docs/drama.py` | 「播放地址」新增「画质」下拉（**选项直接取后端白名单**，避免「文档能选、接口报错」）；`stream` 端点补充「画质写在令牌里」的说明 |
| `locale/en`、`locale/zh_Hant`（含 `.mo`） | 新增 8 条词条并清掉 2 条被替换的死词条，编译后 `django` 2392 条 |

**效果**（实测同一集 `7683196130645003288` 第 5 集）

| | 分辨率 | 视频码率 | 体积 | 转码耗时 |
| --- | --- | --- | --- | --- |
| 改动前（按高度 720） | 408×720 | 1478 kbps | 30.8 MB | 24 s |
| 改动后（`q=1080`，默认档） | **1080×1920** | 2177 kbps | 46.5 MB | 37.6 s |

（本机 nvenc 因驱动过旧不可用，自动回退 qsv；libx264 兜底档走 CRF 20。）

**注意**：产物路径改了，旧布局的 `{DIR}/{剧集}/{集}.mp4` 成为**孤儿文件**（不再被引用，需要时会按新档位重新生成）。

**验证**：`parse_quality` 的空值 / 合法 / 非法（`999`、`abc`）四种口径；`get_play` 的 `data.quality` / `data.ready` 与令牌解码结果（`{sid, ep, w}`）；HTTP 实测 `q=1080` 出流 `206` / `video/mp4` / `Content-Range` 总量 46,529,218 字节，`q=720` 未生成时返回 `202`，`q=999` 与 `q=abc` 返回 20003，不传 `q` 用默认档 1080；文档页画质下拉渲染 5 个选项、默认选中 1080、播放器自动加载该档。回归 `test_hongguo_drama.py` **28/28**、`test_service_policy.py` **120/120**。

### 13. 重构：官网首页与文档中心全面重做，并新增超管「官网外观」模块（4 套可切换的视觉气质）

**关键设计：气质与主题解耦**

### 22. 修复：转码状态记在进程内存里 —— 部署重启后某集永久卡在「正在生成播放地址」

**现象**：线上某集点播一直返回

```json
{"code": 10000, "msg": "正在生成播放地址，请稍候重试", "data": {"state": "running", "elapsed": 817}}
```

`elapsed` 一路涨到十几分钟，但服务器上**一个 ffmpeg 进程都没有**、CPU 负载 0.28 —— 根本没在转。

**根因（两个缺陷叠加）**

1. **「是否正在转」记在进程内存里**（`_JOBS` 字典）。uwsgi 多 worker（尤其刚加的 `lazy-apps`，每个 worker 一份内存）下状态会分裂：真正在转的 worker 说 running，其他 worker 只会塞一条**永不清除**的占位 `running` —— 于是 `elapsed` 一直涨、前端永远在轮询。
2. **锁文件没有属主存活校验**，只按「mtime 超过 `_STALE_LOCK_SECONDS`（1800 秒）」判陈旧 —— 属主进程被 kill 后，必须**干等 30 分钟**才有人能接管。

**触发路径（本次事故）**：21:57 某次点播开始转码并抢到锁 → 22:02 为装 JDK 17 / 配 `HONGGUO_JAVA_BIN` **重启了 uwsgi**，把那个 worker 和转码线程一起杀掉，锁文件残留 → 之后所有轮询都无法启动转码，只能返回占位 running。时间线吻合：`22:07:17 + 817s = 22:20:54`，正是前端看到的那次轮询。

**处置**：删掉僵尸锁后，同一集 **30.3 秒**转完（libx264 软编，1080×1920 / 36.5MB），可正常播放。

**改法**（`SpiderServices/dramas/hongguo/transcode.py`）—— 把「进行中」的唯一真相放到锁文件：

| 改动 | 说明 |
| --- | --- |
| **锁文件即状态** | 内容仍是属主 pid，**mtime 即开工时间**；`job_status` 的 `elapsed` 由文件推算（不再依赖内存里的 `started`），多 worker 天然一致 |
| **属主存活探活** | 新增 `_pid_alive()`：属主已死 → 该锁即僵尸锁；`_acquire_lock_file()` 遇到僵尸锁**立刻删掉重抢**，不再干等 30 分钟（mtime 超时保留为兜底，覆盖 pid 复用等情形） |
| **僵尸锁如实上报** | `job_status` 遇僵尸锁报 `pending`（清锁与接管交给 `ensure()`），不再报 running 骗前端 |
| **去掉占位内存态** | 删掉 `ensure()` 里「别的进程在转 → 给自己塞一条 running」的逻辑；`_JOBS` 只保留失败原因（失败不必跨进程共享；其余 worker 看到 pending 会各自重试一次） |
| **释放锁加归属校验** | 新增 `_release_lock_file()`：只删**自己**的锁，避免误删已被别人接管的锁 |
| ⚠️ **Windows 探活** | `os.kill(pid, 0)` 在 Windows 上会**真的 TerminateProcess 杀掉进程**（CPython 文档明确说明），故 Windows 分支改用 `OpenProcess` + `GetExitCodeProcess` 查询 |

**验证**

| 项 | 结果 |
| --- | --- |
| 新增回归脚本 | `scripts/test_hongguo_stream_lock.py` **24/24 通过**（离线、秒级：产物目录指向临时目录、`_transcode` 换桩，不联网也不起 ffmpeg） |
| 覆盖的契约 | 僵尸锁立刻接管（< 2s）、属主存活时不重复转码、`elapsed` 由锁文件推算、失败落状态并释放锁、释放锁只删自己的、产物就绪时忽略锁内容、**5 个并发只启动 1 次转码** |

| 线上实测 | 清除僵尸锁后该集 30.3s 转完；完整链路（签名取流 → 解 spade key → ffmpeg CENC 解密 → 落盘）产出 `h264 / 1080x1920` 可播文件 |

### 23. 新增：API 服务策略支持「一条策略覆盖多条线路」（线路多选）

**背景**：一个服务下往往有很多条线路，此前一条策略只能挂一条线路（或整条服务级），想让其中几条线路共用同一套状态 / 认证配置，就得建好几条一模一样、还得一起维护的策略。需求是「新建策略时线路可多选」。经确认的口径：**一条策略覆盖多条线路**（不是批量建多条）、**只有线路多选**（端点仍单选）、选中的线路若已被别的策略占用则**原策略让位**。

**改动**

| 位置 | 改动 |
| --- | --- |
| `API/models/Auth/policy.py` | 新增 `extra_prefixes`（`JSONField`，主前缀之外的其余线路）；新增 `all_prefixes` 属性（主前缀 + 附加前缀）；`clean()` 改为**逐前缀**校验层级形状，并要求多线路同属一个服务、前缀不重复 |

| `API/common/middleware.py` | `_policy_nodes()` 把一条策略按 `all_prefixes` **展开成多个节点**（同一策略 id），于是多线路各自参与前缀匹配、命中后按前缀长度降序走同一套继承链；白名单按 id 归属的语义不变 |
| `API/website/console.py` | 新增 `_derive_prefixes()`（服务 + 线路多选 + 端点单选 → `(level, [前缀...])`）与 `_let_existing_yield()`（让位）；`_policy_form_data()` 去掉「路径重复即报错」，改为写主前缀 + `extra_prefixes`；列表页逐前缀给出中文路径标签。原 `_derive_prefix()` 保留给「接口公告」等单选调用方 |

### 4. 变更：红果短剧第 4 集+ 改为「外部托管 + 链接登记」（下线服务端出流）

**背景**：第 3 条把 `/stream` 做成了「免签名 + 时效令牌」，但小影影视随后实测反馈：第 4 集及以后的流是 **H.265/HEVC**（`hvc1`），桌面 Chrome / Edge / Firefox 基本解不了（`videoWidth=0`）。核查后确认这是**源站的硬约束**，不是配置问题：

- 源站第 4 集+ **只下发 HEVC**：第 4/5 集各 5 条轨道（360p~1080p）全部 `codec_type=bytevc1`；源站字段 `gear_des_key` 自证 `MP4|encrypt|h265_hvc1`。
- **拿不到 H.264**：实测 12 组 biz_param 变体（`use_os_player` / `need_mp4_align` / `device_level` / `video_platform` = 1/2/4/8/2048/4096/0），`video_platform` 只接受 1024（其它值 `code=100001 参数错误`），其余变体返回的**仍全是 bytevc1**。
- **没有明文 / m3u8 通道**：直链是 CENC AES-CTR 加密的，浏览器拿到密文播不了；红果 App 能播是因为自研播放器 `libttmplayer` 在**客户端**解密 + 硬件 HEVC 解码。
- 转码成本实测（`veryfast`/`crf 23`）：H.264 1080p **128.5s/集**、体积 ×3.6；720p **71.6s/集**、体积 ×2.1 —— 在「千人同时访问」量级下服务端出流不可行。

**决策**：下线服务端出流，改为「**预处理导出 → 人工上传外部平台 → 登记链接 → 接口返回**」，播放流量不再经过本站。

### 7. 新增：红果短剧第 4 集及以后「网页直出」（免人工、即点即播）

**背景**：第 4 条把第 4 集+ 做成「预处理导出 → 人工上传外部平台 → 登记链接」，可播但要人工逐集处理，剧一多就不可行。用户要求「做一个可以直接播放红果视频的功能，不要每次都上传全部短剧转码」，且明确**只要浏览器端能用**。

**定性与实测（决定方案的硬事实）**

- 解密不是障碍：App 接口给的 `main_url` 是**明文 https 直链**，**不带任何请求头**就能 `Range` 拉取（实测 206、`Content-Range` 正常、`Access-Control-Allow-Origin: *`），文件头是 `ftyp→moov`（天然 faststart）且 `encv/tenc/sinf` 齐备（标准 CENC）；**带 `Referer` 会 403**。内容密钥我们本地纯 Python 就能从 `spade_a` 算出。
- 浏览器是真障碍：实测 Chrome 154（Windows）`canPlayType('hvc1')` 为空、`MediaSource.isTypeSupported('hvc1')` 为 false、`VideoDecoder.isConfigSupported('hvc1')` 也为 false —— **原生 / MSE / WebCodecs 三条路全断**。故「网页能播」只能是 H.264，必须转码。
- 调研三个同类开源项目（`N3urda/hongguoTV`、`Erlmo/shortplay`、`KEJIYUNB/hongguo` + `zhoufuweigg/guoapp`）结论一致：**没有任何项目拿到过明文直链**，能播第 4 集+ 的全是「拿到地址 + 密钥后自行解密」，且都依赖原生播放器硬解 HEVC。故浏览器方案只能转码。

**改动**

### 3. 修复：文档中心在线调试调用流式接口报 500（AI / DeepSeek 的 stream=true）

**现象**：在接口文档中心用「在线调试」测试 AI 接口（`POST /api/ai/BuiltInModel/deepseek`）并把 `stream` 选为 `true` 时，调试面板返回 500，服务端日志为：

```
File "API/website/docs_views.py", line 216, in call
    raw = response.content.decode('utf-8', 'ignore')
AttributeError: This StreamingHttpResponse instance has no `content` attribute.
```

**根因**：`stream=true` 时 AI 接口返回的是 SSE 流式响应（`StreamingHttpResponse`），而在线调试代调只会按普通响应读取 `response.content` —— 流式响应没有该属性。**与 DeepSeek 服务本身无关**（同一接口 `stream=false` 正常返回）。

**影响面核查**：全项目读取响应体只有两处——本处与调用统计的 `business_code()`（其本就带 `not response.streaming` 守卫），无同类盲点；返回流式响应的接口全项目仅 AI 这一个。

**验证**：`/docs/_call/` 转发 AI 接口，`stream=false` → 200 / `application/json` / 正常回复；`stream=true` → **200**（原为 500）/ `text/event-stream` / SSE 内容完整可读且含 `[DONE]`。

1. **认证被拒的请求不进日志与统计**：`ApiRequestLogMiddleware` 原注册在 `ApiAuthMiddleware` **内层**，而认证失败由外层直接返回、不会向下调用。已把它提前到认证中间件之前（仍能读到下行阶段挂上的 `request.auth_app`）。

### 3. 修复：超管页登录跳转死循环

**现象**：已登录的**普通用户**访问任一超管页（`/console/projects/`、`/console/categories/`、`/console/stats/`）时浏览器报 `ERR_TOO_MANY_REDIRECTS`。

**根因**：`superadmin_required` 把非超管跳转到 `/login/?next=<超管页>`，而登录页 GET 的判定是 `if _current_user(request) or is_admin: return redirect(next_url)` —— 「已登录的普通用户」也满足条件，于是回跳超管页 → 再被打回登录页，成环。

值得注意的是设计意图本就写在 `API/website/admin_auth.py` 的注释里（「普通用户即便回跳也进不去（防循环：普通登录一律回首页）」），只是实现漏了「已登录普通用户」这条路径。

**修复**：把「是否按 `next` 回跳」的判定从 `已登录 or 超管` 收紧为**只有超管**；已登录的普通用户一律回首页。

**验证**（逐跳跟随重定向，均 2 跳内收敛）

| 场景                   | 链路                                           | 结果        |
| -------------------- | -------------------------------------------- | --------- |
| 普通用户 → 超管页           | `/console/stats/` → `/login/?next=...` → `/` | 200       |
| 普通用户 → 登录页(next=超管页) | `/login/?next=...` → `/`                     | 200       |
| 超管 → 登录页(next=超管页)   | `/login/?next=...` → `/console/stats/`       | 回跳仍生效，200 |
| 匿名 → 超管页             | `/console/stats/` → `/login/?next=...`       | 渲染登录页，200 |
