# 数据库模型创建规则

> 本规则约束 `API/models/` 下**新建**模型的组织方式（文件夹 / 文件如何搭、哪些模型写进同一文件）。
> 核心一句话：**文件夹按业务域建，文件按强关联聚合合，通用模型放根目录。**

---

## 一、核心思想

| 维度 | 规则 | 示例 |
|------|------|------|
| 文件夹 | 代表一个**业务域**（功能域），用 PascalCase 命名 | `Users/`、`Projects/`、`Auth/`、`Music/` |
| 文件 | 代表一个**强关联聚合**：彼此必不可分的模型写进同一个文件 | `Users/user.py`（User + UserToken） |
| 根目录 | 放**通用模型**（跨业务复用、不专属某个业务域） | （当前无存量通用模型，按需新增） |
| 层级 | **最多两层**：业务域文件夹 → 模型文件，不继续嵌套 | `API/models/Users/user.py` |

---

## 二、目录组织规则

```
API/models/
├── __init__.py          # 汇总导出全部模型
├── 数据库模型创建规则.md   # 本规则文档
├── <通用模型>.py        # 跨业务复用的通用模型（目前为空，按需新增）
├── <业务域>/            # 业务域文件夹（PascalCase）
│   ├── __init__.py      # 导出该域模型
│   └── <功能>.py        # 强关联聚合模型文件（snake_case）
└── ...
```

### 2.1 文件夹 = 业务域

- 以**业务功能**划分文件夹，如 `Users`（用户体系）、`Projects`（接入项目）、`Auth`（接口认证）、`Music`（音乐）、`Email`（邮件模板）、`Feedback`（问题反馈）。
- 文件夹命名用**英文、PascalCase、复数/集合形式**，避免缩写。
- 同一业务域的新模型，**优先加入已有文件夹**，不重复建同名文件夹。

### 2.2 通用模型放根目录

- 判定"通用"：模型**跨多个业务域复用**，不专属任何一个业务域。
- 通用模型直接放 `API/models/` 根目录（当前无存量通用模型，后续新增时按此判定），不进任何业务域文件夹。
- 抽象基类（如 `BaseModel`）属于通用基础设施，继续放 `API/common/base.py`，不占 `models/` 目录。

### 2.3 层级与命名

- **最多两层**：`业务域文件夹 → 模型文件`，禁止继续嵌套子文件夹。
- 文件夹：PascalCase（`Users`、`Projects`、`Auth`）。
- 文件：snake_case（`user.py`、`app.py`、`category.py`）。

---

## 三、同文件聚合规则（判断"必不可分"）

哪些模型**必须写进同一个文件**？满足以下任一条件即判定为"强关联聚合"：

1. **直接外键关联**：一方对另一方存在 `ForeignKey`，脱离关联无法独立使用。
   - 例：`UserToken.user` → `User`；`MusicSource.music` → `Music`。
2. **同一聚合根**：子实体离开父实体毫无意义，必须同生共死。
   - 例：`UserToken` 离开 `User` 无意义，两者同写 `Users/user.py`。
3. **共享强耦合逻辑**：同业务域内共享常量 / 校验逻辑，拆开会造成重复定义或引入循环导入。
   - 例：`ApiCategory` 的自关联树与认证三态（`inherit/auth/open`）归属同一认证体系。

### 3.1 反例（应拆分的情形）

- 两个模型**无外键、无聚合关系、业务域不同** → 各自独立文件，绝不凑在一个文件里。
- 同一业务域内**关系松散的独立实体** → 按聚合拆分到不同文件（一个文件一个聚合）。

### 3.2 现有代码对照（参考）

| 文件 | 模型 | 聚合依据 |
|------|------|----------|
| `Users/user.py` | `User` + `UserToken` + `UserVerifyRecord` | 外键关联 + 同一聚合根（Token/验证记录绑定用户与项目） |
| `Users/auth_method.py` | `AuthMethod` | 认证方式开关，独立实体 |
| `Projects/app.py` | `UserApp` | 单一模型，自成一文件 |
| `Auth/category.py` | `ApiCategory` | 自关联树，单一聚合 |
| `Music/music.py` | `Music` + `MusicSource` | 外键关联（播放源脱离音乐无意义） |
| `Email/email_template.py` | `EmailTemplate` | 单一模型（邮件模板按 type 区分用途） |
| `Feedback/feedback.py` | `Feedback` + `FeedbackReply` | 外键关联 + 聚合根（追加脱离反馈无意义） |

## 四、命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 业务域文件夹 | 英文 PascalCase 复数/集合 | `Users`、`Projects`、`Auth` |
| 模型文件 | 英文 snake_case 单数 | `user.py`、`category.py`、`app.py` |
| 模型类 | 英文 PascalCase 单数 | `User`、`UserToken`、`ApiCategory` |
| 外键 related_name | 英文复数，语义清晰 | `related_name='tokens'`、`related_name='children'` |
| db_table | snake_case 单数 | `user`、`user_token`、`api_category` |
| verbose_name | 中文，可读 | `'用户'`、`'登录凭证'` |

---

## 五、导入与导出

- 文件内一律**绝对导入**（`from API.xxx import yyy`），禁止相对导入。
- 每个业务域文件夹的 `__init__.py` 导出该域模型：

```python
# API/models/Users/__init__.py
from API.models.Users.user import User, UserToken

__all__ = ['User', 'UserToken']
```

- 根目录 `__init__.py` 汇总导出全部模型，供 `admin.py`、迁移、业务代码统一引用。

---

## 六、新建模型决策流程

新增一个模型时，按以下顺序判断：

1. **是抽象基类？**（如 `BaseModel`）→ 放 `API/common/base.py`，结束。
2. **跨业务通用？** → 放 `API/models/` 根目录新建文件，结束。
3. **归属哪个业务域？** → 进入（或创建）对应业务域文件夹。
4. **与文件夹内已有模型强关联？**（见第三章判定）→ 是则写入同一文件；否则新建独立文件。
5. 补全：文件头 docstring、`Meta`（中文 `verbose_name`）、`__str__`、`__init__.py` 导出、根 `__init__.py` 汇总。

---

## 七、存量与生效范围

- **约束范围**：本规则约束**新建**与**后续调整**的组织方式。
- **存量组织现状**：模型已全部按业务域目录组织（`Users/`、`Projects/`、`Auth/`、`Music/`、`Email/`、`Feedback/`），根目录仅保留 `__init__.py` 汇总导出与本规则文档。
- 调整存量文件组织时，**只移动文件位置与导入路径**，禁止改变模型字段 / Meta / db_table / 迁移历史；涉及历史迁移引用的（如 `RawJSONEncoder`），同步调整迁移文件的 import 指向新路径。
- 新增模型一律按本规则组织。
